# Apple authorization and distribution gate

**Access date:** 2026-10-10
**Scope:** Apple’s authorization path for macOS cross-architecture execution and the possibility of distributing an authorized runtime to unrelated Macs. This is a documentation review only; no Apple request was submitted.

## Decision summary

**Gate 0A — development authorization: UNKNOWN.** Apple publicly documents a general route for requesting managed capabilities, but I found no Apple-published documentation naming `com.apple.developer.cross-architecture-support`, `com.apple.developer.cross-architecture-support-unmanaged`, or “Cross-architecture Compatibility Framework.” Their absence from public references does not establish that Apple will not grant them. It leaves the route, eligibility, and exact profile requirements unverified.

**Gate 0B — Developer ID distribution: GENERIC PATH VERIFIED; WinFerry capability UNKNOWN.** Apple supports direct macOS distribution with Developer ID signing and notarization. Its documentation says Developer ID provisioning profiles apply to all devices, unlike development profiles that enumerate registered devices. That supports distribution without enrolling or registering each recipient Mac for ordinary Developer ID software. However, Apple also says some entitlements are not supported by Developer ID profiles. No public Apple source found here confirms that the cross-architecture entitlement can be put in a Developer ID distribution profile. Therefore the requested end-to-end distribution model is not yet proven.

The practical gate is not whether Developer ID and notarization exist; they do. It is whether Apple will provision this exact entitlement for a WinFerry App ID in a **Developer ID** profile, and whether that profile remains valid when embedded in a notarized release bundle used on an unrelated stock Mac.

### What “without enrollment” can and cannot mean

For a regular Developer ID release, Apple’s documented direct-distribution flow does not ask the publisher to register each customer Mac. Developer ID profiles are described as applying to all devices; development profiles instead carry registered test-device identifiers. This supports the desired recipient experience in principle.

The publisher still needs the signing credentials and any profile Apple requires. If WinFerry’s profile is a Developer ID profile containing the exact restricted entitlement, Apple’s documentation indicates that Gatekeeper evaluates the certificate at installation and evaluates the embedded profile at installation and every launch. A profile expiring or being revoked can therefore affect an installed runtime. This makes the profile lifecycle and renewal terms part of the feasibility decision, not just build-time details. [Developer ID certificates](https://developer.apple.com/help/account/certificates/create-developer-id-certificates/)

Apple’s current public macOS capability table lists the capability families it supports by membership and certificate type, but it does not list the cross-architecture item by name. That is evidence only about the public table. A hidden portal entry, a new capability not yet documented, or a manually assigned entitlement remains possible and requires a direct account/process check or written Apple response.

## Documented route to pursue

1. Use an explicit App ID for the signed WinFerry host/loader bundle. If the capability appears in that App ID’s **Capability Requests** tab, have the team Account Holder submit the request and retain Apple’s criteria and status record. Apple says managed-capability requests are submitted there and then enabled on the App ID after assignment.
2. If the capability does not appear, use Apple Developer Support’s account/contact process and ask specifically for the entitlement request route. Apple’s support page says entitlement requests are made through entitlement forms and status updates continue in the resulting email thread. The Account Holder should include the exact key(s), capability display name if shown, bundle ID, supported OS versions, a minimal test case, and the requested development and distribution use cases.
3. Treat approval for development as a separate result from approval/provisioning for Developer ID distribution. Inspect the generated profiles themselves and confirm the authorized entitlement is present in both the macOS development profile and a Developer ID profile before considering Gate 0A or Gate 0B passed.

Apple sources: [Capability Requests](https://developer.apple.com/help/account/capabilities/capability-requests/), [Apple Developer code-level support](https://developer.apple.com/support/technical/), [Supported capabilities (macOS)](https://developer.apple.com/help/account/reference/supported-capabilities-macos). The support page requires an Apple Developer account for some support services; its exact entitlement form may require signing in. No form was submitted during this research.

## Questions for Apple

Submit these as one focused authorization request through the Account Holder’s Apple Developer contact channel. Ask for written answers tied to the WinFerry team and App ID:

1. Are `com.apple.developer.cross-architecture-support` and `com.apple.developer.cross-architecture-support-unmanaged` current supported entitlement keys? What is the official capability name and supported macOS version range?
2. What is the official request path for each key? Can an individual using a free Apple Developer account request the unmanaged variant for local development, or must the team be enrolled in the paid Apple Developer Program? Is approval team-wide or limited to a specific App ID?
3. Can the approved entitlement be included in a **Developer ID distribution provisioning profile** for an independently distributed macOS app? Is it restricted to Mac Development or ad hoc profiles? Does the recipient need to install a separate profile, register a device, enroll in a developer program, use MDM, or contact Apple at first launch?
4. Can a public open-source project distribute a notarized app bundle containing the Developer ID profile tied to its own App ID? Does the profile authorize the host loader, child processes, or both? Must each entitled executable be separately bundled/signed, or is one authorized host process sufficient for the required cross-architecture child launch?
5. Is Developer ID signing plus notarization supported with this entitlement and Hardened Runtime on stock macOS with SIP enabled? What signing, provisioning, or notarization errors should be expected when the capability is missing or limited to development?
6. What are the profile validity, renewal, revocation, and migration rules for this entitlement? If the team or App ID changes, must the entitlement be re-requested?

## Gate acceptance criteria

**Gate 0A passes only when** Apple’s authorization is issued for the WinFerry team/App ID; a correctly signed and provisioned test bundle contains the authorized entitlement; and the controlled 4 KB child-process experiment launches and reports the expected page size on a stock development Mac with SIP enabled.

**Gate 0B passes only when** the same entitlement is present in a Developer ID distribution profile accepted by Apple’s signing/notarization path, and a clean install/launch succeeds on an unrelated stock Apple Silicon Mac without the recipient registering the Mac, joining a developer team, installing a development profile, or changing system security settings. A development profile or the developer’s own machine is not evidence for Gate 0B.
