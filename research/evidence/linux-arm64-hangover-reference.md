# ARM64 Linux reference path: Hangover + Wine ARM64EC + FEX

Research cutoff: **2026-10-10**. This combines pinned source/documentation review with a locally performed ARM64 Linux reference experiment. **VERIFIED** identifies direct primary-source evidence or a locally reproduced result; its scope is stated each time. **REPORTED** means an upstream user or maintainer supplied runtime evidence. **INFERRED** means a technical conclusion from evidence. **UNKNOWN** means the reviewed sources and experiment do not settle the question. The complete local run record is in [the experiment directory](../experiments/linux-arm64-reference/README.md).

## Finding

**INFERRED — Hangover is the best existing reference for a free ARM64 Linux execution path that can continue WinFerry work before Apple grants any macOS capability.** It already combines ARM64 Wine, Wine's ARM64EC ABI, and FEX's ARM64EC Windows PE frontend. It keeps Wine's Unix side native and translates application code, rather than running a whole x86 Wine installation under a Linux emulator. This is a reference architecture for a Linux guest, not evidence that WinFerry's Darwin loader or native macOS runtime works.

**VERIFIED locally — Hangover 11.16 ran both a source-built ARM64 Windows console program and a minimal x86-64 PE through FEX in an ARM64 Ubuntu guest.** The ARM64 app called `GetStdHandle` and `WriteFile`, printed the expected line, and returned 37. The x64 app also printed the line and returned 37 in five later runs across five fresh Wine prefixes; logs confirm `libarm64ecfex.dll` selection. This proves one tiny x64 path can execute, not broad compatibility or production stability. An earlier prefix produced two `0xc000001d` assertions at `FEXCore::Assert::ForcedAssertEv` before output. The problem did not recur across the five clean-prefix trials, including one with isolated `HOME`, XDG, and FEX app-data/config/cache directories. Its trigger remains unknown. A Hangover user reported the same exception class with release 10.14 in [issue #211](https://github.com/AndreRH/hangover/issues/211); that is context, not evidence of a shared cause. See the [local logs and hashes](../experiments/linux-arm64-reference/README.md).

## Execution architecture

**VERIFIED — Hangover's split is at the Windows/Wine boundary.** Hangover says it emulates the Windows application but executes Wine's Windows/Wine system-call implementations and Unix-facing work outside the emulator. The x64 path uses ARM64EC plus FEX; `libarm64ecfex.dll` is the documented/default 64-bit emulator module and can be selected with `HODLL64`. Wine also runs ARM64 Windows PE applications natively. This design avoids translating Wine's Unix host process along with the application and does not require 32-bit Unix libraries. [Hangover 11.16 README](https://github.com/AndreRH/hangover/blob/56e385b7ff490edd281b288f420677093563560b/README.md).

**VERIFIED — This is FEX's Windows PE integration, not the standalone Linux frontend.** Hangover's build guide cross-compiles `libarm64ecfex.dll` for `arm64ec-w64-mingw32` and installs it in Wine's `aarch64-windows` directory. In contrast, standalone FEX's normal Linux frontend requires an x86-64 Linux root filesystem. The Hangover ARM64EC-DLL build/run recipe does not list that Linux root filesystem as a dependency. Do not install or configure standalone FEX's x86-64 rootfs for the first Hangover test unless separately testing FEX's Linux frontend. [Hangover build guide](https://github.com/AndreRH/hangover/blob/56e385b7ff490edd281b288f420677093563560b/docs/COMPILE.md), [FEX README](https://github.com/FEX-Emu/FEX/blob/14c92681f4d62cf84d901460e0358de09c8847a7/Readme.md).

For Hangover, ARM64EC gives translated x64 code a Windows-defined interop path into Wine's native ARM64EC implementation. FEX supplies the x64 instruction translation and PE module; Wine supplies process creation, Windows API behavior, host threads and graphics/windowing. The syscall/Unix split is why this is a more pertinent reference than launching all of Wine through FEX. The exact performance benefit is a maintainer's architectural claim and benchmark result, not a WinFerry measurement. [Hangover architecture and benchmarks](https://github.com/AndreRH/hangover/blob/56e385b7ff490edd281b288f420677093563560b/README.md), [Hangover benchmark notes](https://github.com/AndreRH/hangover/blob/56e385b7ff490edd281b288f420677093563560b/benchmarks/readme.md).

FEX's current upstream build gate accepts Linux and Windows host systems and rejects other systems; its README describes ARMv8.0-A-or-newer hardware and lists FEAT_FP and FEAT_CRC32 as minimum extensions. That is consistent with running the ARM64 Linux host frontend in a Linux VM and the PE ARM64EC frontend inside Hangover. It is not an endorsement of a Darwin FEX host port. [FEX host-system check](https://github.com/FEX-Emu/FEX/blob/14c92681f4d62cf84d901460e0358de09c8847a7/CMakeLists.txt#L56), [FEX host prerequisites](https://github.com/FEX-Emu/FEX/blob/14c92681f4d62cf84d901460e0358de09c8847a7/Readme.md).

## Build instructions and upstream CI

**VERIFIED — Hangover publishes a source build recipe.** It asks for the Wine 64-bit build dependencies, `llvm-mingw` for PE cross-compilation, and approximately 5 GB of disk for Wine. Its Wine configure line is `--disable-tests --with-mingw=clang --enable-archs=arm64ec,aarch64,i386`. The FEX ARM64EC PE DLL is an additional build: use the FEX-provided MinGW toolchain file and `MINGW_TRIPLE=arm64ec-w64-mingw32`; the guide estimates approximately 1.5 GB of disk. These are disk estimates, not memory requirements. The minimum useful self-build is Wine plus `arm64ecfex`; Box64 and the separate 32-bit emulator builds are unnecessary for an x64-only smoke test. [Pinned Hangover COMPILE.md](https://github.com/AndreRH/hangover/blob/56e385b7ff490edd281b288f420677093563560b/docs/COMPILE.md).

**VERIFIED — upstream CI builds ARM64 package artifacts.** The workflow builds the FEX PE ARM64EC package and extracts `libarm64ecfex.dll`; it builds Hangover Wine packages for ARM64 and bundles the ARM64 `.deb` artifacts. The current workflow includes `ubuntu-24.04-arm` for newer Ubuntu Wine builds, while the FEX PE frontend is built in its package job. The inspected workflow is a packaging/build pipeline, not an x64 Windows runtime test: no test job or execution check was present in the reviewed workflow. Consequently, successful CI packaging is not the same evidence as executing an x64 PE through Wine+FEX. [Hangover package workflow](https://github.com/AndreRH/hangover/blob/master/.github/workflows/deb.yml), [release package list](https://github.com/AndreRH/hangover/releases/tag/hangover-11.16).

The release README lists Debian 11/12/13 and Ubuntu 20.04/22.04/24.04/25.10 packages. For a first VM experiment, Ubuntu Server ARM64 24.04 is a convenient supported package target. Using a release package is preferable to building Wine and FEX on an 8 GB Mac: it tests the runtime boundary while avoiding an unmeasured multi-component compile workload. If a later source-build milestone is needed, pin the tag and submodules above and compare the built modules before attempting Darwin integration.

## Host and VM requirements, with caveats

| Requirement | Finding and confidence |
|---|---|
| Host ISA / OS | **VERIFIED locally:** macOS 27.0 on an Apple Silicon M1 MacBook Air ran Colima 0.7.6 using the `vz` virtualization backend. The guest/container reports `aarch64`; the Windows PE execution path used that ARM64 Linux guest, not a Linux x86-64 emulator or Rosetta-on-Linux. UTM was not used. [Local host/guest record](../experiments/linux-arm64-reference/README.md). |
| CPU features | **VERIFIED locally:** `/proc/cpuinfo` exposed `fp`, `asimd`, and `crc32` among other ARM64 features. **INFERRED:** The visible CPU includes the two minimum feature classes documented by FEX; this does not explain or waive the FEX assertion. [FEX prerequisites](https://github.com/FEX-Emu/FEX/blob/14c92681f4d62cf84d901460e0358de09c8847a7/Readme.md). |
| Page size | **VERIFIED locally:** `getconf PAGESIZE` returned `4096` in the Ubuntu 24.04.5 ARM64 guest used for the test. The host macOS page size and the Linux guest page size are separate. Hangover's wiki notes the 4 KB expectation and asks for retesting after relevant Wine changes. [Hangover Page Size note](https://github.com/AndreRH/hangover/wiki/Page-Size). |
| Memory/disk | **VERIFIED locally:** the Colima profile was configured for 3 GiB and 2 vCPUs; the container saw about 2.8 GiB memory and a 23 GiB overlay at test time. This is one successful small ARM64 Wine run, not a minimum requirement or a source-build capacity result. |
| Graphics | **INFERRED:** No D3D or GUI is needed to prove the translator/Win32 API path. Begin with a console executable and do not include DXVK, Vulkan, or GPU sharing. |
| Entitlements/Rosetta | **INFERRED:** Linux guest execution does not exercise Apple's restricted macOS 4 KB process entitlement and does not require Rosetta. It cannot answer the separate native-Darwin authorization/distribution question. |

The 4 KB caveat is important: older ARM64 Linux distributions and kernels can differ in page granule. A Linux guest has its own kernel and page size; do not infer its page size from macOS's page size. The Hangover wiki mentions Asahi Linux's 16 KB default and describes using its VM approach as a possible workaround, while explicitly noting that this was not tested by that wiki author. For this POC, choose an ARM64 guest whose own `getconf PAGESIZE` is 4096 rather than assuming a VM solves the requirement. [Hangover Page Size note](https://github.com/AndreRH/hangover/wiki/Page-Size).

## What upstream runtime evidence establishes

**REPORTED — ARM64EC/FEX has been observed running an application, but the trace is not a clean console proof.** In Hangover issue #188, opened May 22, 2025, an ARM64 Linux user logs a Windows application launch. Wine prints `starting ... in experimental ARM64EC mode`, then `starting FEX ... libarm64ecfex.dll`; logs from the Windows app appear later. The same trace includes failed large virtual-address allocations and service errors. It supports that Wine selected the ARM64EC/FEX path and that execution progressed into an application, but it does not establish broad compatibility, the target's exact PE machine type, a successful exit, a tiny console result, or a current 11.16 run. [Hangover issue #188](https://github.com/AndreRH/hangover/issues/188).

**VERIFIED — project documentation exposes the execution command; local evidence checks module selection.** Hangover documents `wine your_x86_64_application.exe` with the FEX module as its default, and lets `HODLL64` select it. The local log shows the x64 PE loaded and `libarm64ecfex.dll` selected, but execution stopped at FEX's forced assertion. Release bundles include the ARM64 Wine and FEX packages. [Hangover README](https://github.com/AndreRH/hangover/blob/56e385b7ff490edd281b288f420677093563560b/README.md), [release](https://github.com/AndreRH/hangover/releases/tag/hangover-11.16), [local run log](../experiments/linux-arm64-reference/results/x64.stderr).

**UNKNOWN — no upstream CI smoke test was found.** The reviewed workflow demonstrates that the packages build and bundle. The source examined did not include a pinned x64 console test executable, expected stdout/exit code assertion, or a runtime trace as part of CI. This is a bounded search result, not proof that no upstream user has ever run a console program.

## Local reference experiment (performed)

On 2026-10-10, a Colima `vz` profile ran Ubuntu 24.04.5 ARM64 with 4 KB pages and two visible CPUs. The published Hangover 11.16 Ubuntu 24.04 ARM64 packages were installed after enabling verified HTTPS package metadata inside the disposable container. No UTM or Rosetta-on-Linux path was used.

A single WinFerry-authored console source was cross-compiled into AMD64 and ARM64 PE binaries with llvm-mingw 20261006. The ARM64 PE passed its Win32 console API check. The AMD64 PE selected `libarm64ecfex.dll` and passed five later runs across five fresh Wine prefixes, with the expected output and return code 37. The first Wine prefix produced two earlier x64 failures: Wine returned 29 after `EXCEPTION_ILLEGAL_INSTRUCTION` (`0xc000001d`) and the app printed nothing. The exception PC was within the FEX module's `.text`; disassembly identifies `FEXCore::Assert::ForcedAssertEv` (`hlt #1`). The failed prefix and the later fresh-prefix passes used the same Hangover/FEX package. The failure trigger and the reason it was confined to one prefix remain UNKNOWN.

Full reproduction inputs, hashes, process output, logs, and the experiment script are in [the experiment directory](../experiments/linux-arm64-reference/README.md). This validates one ARM64 Win32 console path and one very small x86-64 FEX execution path on this Linux guest, while exposing a prefix-local assertion anomaly that still needs explanation. It does not validate macOS, Apple authorization, graphics, GUI, or distribution.

## WinFerry implication

**INFERRED — continue work without paying for a developer account.** Use the passed ARM64 and x64 console runs as small shared-stack baselines, then diagnose why one Wine prefix hit an FEX assertion twice while five fresh prefixes passed. Keep native Darwin work isolated and build-only until Gate 0A. Do not port all of Linux FEX into macOS from this reference: Hangover's lower-scope seam is its FEX ARM64EC PE module loaded by native Wine, while the standalone FEX Linux frontend has Linux host assumptions. These Linux runs do not resolve Apple's Gate 0A or Gate 0B questions.
