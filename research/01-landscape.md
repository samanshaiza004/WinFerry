# Comparative landscape

Research cutoff: **2026-10-10**. VERIFIED means inspected source/documentation supports the stated fact; REPORTED means upstream says an execution result exists but this investigation did not reproduce it; INFERRED is an engineering judgment; UNKNOWN marks missing evidence. A repository README claim is not a local runtime test. Mutable branch references are explicitly recorded in [evidence](evidence/landscape-sources.md); do not mistake them for immutable build pins.

## The 2026 change that matters

**VERIFIED announcement / REPORTED execution:** CodeWeavers announced native ARM64 macOS CrossOver Preview on **July 31, 2026**. Wine developer Brendan Shanks's **August 7** explanation identifies ARM64 Wine plus FEX for i386 and x86-64/ARM64EC execution. This invalidates the older claim that all macOS Wine execution necessarily uses Rosetta. It does **not** establish that a separately built, freely provisioned, distributable runtime has been reproduced here. The blog article returned HTTP 403; its official index and the maintainer's Wine-devel explanation remain directly readable. [CodeWeavers announcement index](https://www.codeweavers.com/blog), [Wine-devel announcement](https://list.winehq.org/hyperkitty/list/wine-devel%40list.winehq.org/thread/CKG5CEN2BE5VRXZ7O7NX4YUSBH3247WH/?sort=date).

**VERIFIED platform policy:** Apple’s September 1, 2026 notice says macOS26.4+ may warn when launching Rosetta apps and macOS27 is the final general-support release. It preserves a limited older-game exception, which is not a general runtime guarantee. [Apple announcement](https://developer.apple.com/news/?id=w5ngl9k2).

## Additional relevant evidence

**VERIFIED source scope / REPORTED end-to-end result:** [osxEQL STATUS](https://raw.githubusercontent.com/sowoky/osxEQL/main/docs/STATUS.md) describes self-building CodeWeavers 26.2 LGPL Wine, DXMT 0.80 and bundling the complete dynamically loaded dependency closure. Its instructions explicitly use **Intel dependencies and i386,x86_64 WoW64**, so this is useful packaging evidence, **not ARM64/Rosetta-independence proof**. Header date and later signing section disagree; record section dates separately. [Porthole](https://github.com/Bockit/porthole) explicitly uses x86-64 Wine/Rosetta/DXVK/MoltenVK: another packaging baseline, not the desired runtime.

**VERIFIED alternative scope:** [Blink](https://github.com/jart/blink) tests x86-64 Linux binaries on macOS ARM and has an ISC license. Hangover's README calls its Blink integration started but not included. This is portable-emulator prior art, not a working Wine ARM64EC replacement. **INFERRED:** switching translators without measured FEX failures increases new ABI integration work.

**VERIFIED academic pointer:** Box64's own README links the EuroSys 2026 paper [Practical and Efficient x86-64 Emulation on RISC-V](https://doi.org/10.1145/3767295.3803574). It is relevant translator design literature, not Apple Silicon performance evidence; the full paper was not inspected here. Wine-devel, FEX issues and implementation source are stronger evidence for the immediate Mac decision than unrelated throughput measurements.

## Implication

**INFERRED:** the innovation is a reproducible, independently distributable ARM64 Wine/FEX integration and measurable desktop compatibility, then deterministic deployment and diagnostics. The original stack is no longer a wholly hypothetical CPU/API combination, but its open-source build, Apple security authorization and support boundaries still need independent verification. Never substitute a native launcher screenshot for process/PE-emulator provenance.
