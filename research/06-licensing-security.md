**INFERRED compliance design:** publish a dependency manifest identifying source SHA/tag, patches, compiler, generated artifacts, license and complete corresponding-source archive for every release. Separate UI and runtime artifacts for maintainability, not as an assertion that a process boundary automatically eliminates copyleft duties. Audit recursively, including LLVM, mingw, fonts, codecs, crypto libraries and dynamically loaded libraries. A small runtime's advertised top-level license is not a complete package bill of materials.

Under LGPL 2.1 section 6, dynamically linking can satisfy the requirement to allow a recipient's modified library to work if the appropriate shared-library mechanism is used; static linking may require relinkable application objects or another permitted method. Modification source obligations still exist in either case. Signing and library validation must not silently make user replacement impossible. **UNKNOWN legal details:** final linkage, generated PE DLL packaging, installer aggregation and source-offer strategy should be reviewed against the actual shipped artifact. [LGPL sections 2, 4–6](https://raw.githubusercontent.com/wine-mirror/wine/master/COPYING.LIB).

## CrossOver reuse and Apple's proprietary tools

**VERIFIED:** CodeWeavers publishes FOSS source and identifies GPL/LGPL components separately from its commercial product. **INFERRED:** reuse published Wine patches under their original license, with provenance and notices; do not extract proprietary GUI/assets or D3DMetal from an installed CrossOver. The stable **26.3.0** source listing is not evidence that the July ARM64 Preview's exact Wine/FEX sources and packaging are all independently reproducible. Acquire and verify the specific Preview sources before claiming that. [CodeWeavers source](https://www.codeweavers.com/crossover/source).

**VERIFIED:** Apple's current official GPTK page describes evaluation tooling, Metal Shader Converter and open-source companion skills/samples. **UNKNOWN:** this investigation did not obtain the current GPTK 4 evaluation framework's full accepted license agreement, so it makes no definitive claim about every allowed redistribution scenario. A samples repository does not grant a redistribution license to D3DMetal or the compiler. Exclude both from the mandatory runtime; licensed local comparison experiments can remain optional. [GPTK 4](https://developer.apple.com/games/game-porting-toolkit), [Apple applicable agreements](https://developer.apple.com/support/terms).

## Developer versus recipient enrollment

**VERIFIED:** Apple requires a Developer Program Account Holder to issue Developer ID certificates; notarization scans Developer-ID-signed artifacts. Free registration provides documentation and beta downloads but is not equivalent to this distribution enrollment. **INFERRED:** a maintainer may pay for membership (or qualify for a fee waiver) and ship a free app; ordinary recipients normally do not enroll merely to launch that signed app. These are separate claims from whether Apple will grant and validate the new cross-architecture entitlement to an independent runtime publisher. [Developer ID](https://developer.apple.com/developer-id/), [account distinctions](https://developer.apple.com/help/account/basics/about-your-developer-account).

**UNKNOWN, release-blocking:** independent access to the required cross-architecture support capability, provisioning profile policy, ad-hoc development support and notarized distribution must be established. A free Apple Account cannot be assumed sufficient. CodeWeavers' granted capability cannot be assumed available to all accounts, or borrowed by replacing signed binaries. The local unsigned/ad-hoc process probe did not successfully spawn with 4 KB pages; see experiment evidence and [02](02-native-arm64-wine.md). It does not prove the exact cause or that authorized distribution is impossible.

Apple's general managed-capability and Developer ID flows are documented, but the current public macOS capability table does not list this exact entitlement. The specific account request path and Developer ID profile eligibility are tracked as independent unknowns in [the Apple authorization evidence](evidence/apple-authorization-process.md); passing development authorization alone will not pass distribution Gate 0B.

**VERIFIED general JIT rules:** Apple documents `MAP_JIT`, hardened-runtime `com.apple.security.cs.allow-jit`, a single JIT region for that configuration, and thread write/execute protection. **INFERRED:** Wine/FEX executable guest mappings and self-modification need separate validation, not just generic browser JIT entitlement advice. Audit which hardened-runtime exceptions are actually necessary and test child processes. **Never require disabling SIP.** [Apple JIT guidance](https://developer.apple.com/documentation/apple-silicon/porting-just-in-time-compilers-to-apple-silicon).

**VERIFIED:** UTM explicitly requires a valid Windows license regardless of how its installer was obtained. Microsoft says a unique Windows 11 Pro license is required for each instance, hardware or VM, in its supported Mac scenario; Enterprise licensing adds separate rights. ISO download, emulation support and activation bypasses do not grant free operating-system redistribution. **INFERRED product rule:** fallback attaches to a user's independently licensed installation. Do not distribute a preactivated Windows disk or promise a free Windows license. **UNKNOWN legal issue:** OEM/retail/volume and reassignment rights vary; consult the actual user's applicable terms instead of claiming every license can be transferred. Microsoft authorization of Parallels is documented; absence of that product endorsement for UTM is not, by itself, proof of prohibited use.

## Threat model and safe execution

**VERIFIED longstanding design statement:** Wine is not a sandbox. A compatibility prefix separates Windows state, not authority over the host account. [Wine-devel security discussion](https://www.winehq.org/pipermail/wine-devel/2002-October/009804.html). macOS App Sandbox provides explicit host resource restrictions, but this research has not demonstrated a fully compatible Wine/FEX sandbox profile. [Apple App Sandbox](https://developer.apple.com/documentation/security/app-sandbox).

**INFERRED requirements:** parse PE/MSI metadata without executing it; bound parser work; do not elevate installers; keep a separate per-app prefix; default to no host home-directory mapping and user-selected document import/export; design a sandboxed helper with explicit file grants and optional network permission; ensure loader/wineserver/children inherit constraints. Removing a `Z:` drive symlink alone is not a security boundary. Test malicious fixtures for arbitrary host paths, symlink escape, registry-run child processes, shell execution, local sockets and credential access. Some applications may require features incompatible with strict isolation; explain that permission in the recipe rather than silently widening it.

A VM offers a stronger separate guest boundary but shared folders, clipboard, networking and USB remain escape/interaction surfaces. **INFERRED:** for genuinely untrusted software, favor a disposable VM with sharing/network off and maintained host/guest; do not label either backend malware-proof. Validate notarized release packages after a quarantined download on a fresh user account; test offline launch and every nested executable; separate crash logs from user content and redact paths, tokens and document data by default.

## Upstream sustainability and contribution policy

**VERIFIED:** FEX's CONTRIBUTING states: “No AI/ML/LLM/etc code contributions.” **VERIFIED:** DXMT rejects AI-made/co-authored contributions and permits research findings while asking not to create a PR. This mission submits no patches. Future FEX and DXMT implementation contributions must follow a human-authored path acceptable to those maintainers; do not relabel agent-written code as human-written. [FEX policy](https://raw.githubusercontent.com/FEX-Emu/FEX/main/CONTRIBUTING.md), [DXMT policy](https://raw.githubusercontent.com/3Shain/dxmt/main/CONTRIBUTING.md).

Wine contributions should follow upstream development/submission policy and independent provenance. **INFERRED:** keep a bounded patch stack, budget rebases and record rejected upstream changes with reasons. Use REA/Ghidra only against authorized targets and license-permitted material; keep behavior observations separate from copied proprietary decompilation. No proprietary source reconstruction was performed here. Copyright, anti-circumvention and contractual questions depend on jurisdiction/target and need specialist review before non-public reverse engineering. [REA lawful-analysis disclaimer](https://github.com/morluto/rea#disclaimer).
