Date: 2026-10-10. Acceptance criteria below remain **PROPOSED / INFERRED** unless explicitly marked as current evidence. Engineering priorities derive from the source evidence in [02](02-native-arm64-wine.md), [03](03-fex-hangover.md), [04](04-graphics.md), alternatives in [05](05-alternatives.md), and the [Linux reference experiment](experiments/linux-arm64-reference/README.md). ## Current evidence

**VERIFIED 2026-10-10:** Hangover 11.16 in an ARM64 Ubuntu 24.04.5 guest ran source-built ARM64 and AMD64 Windows console PEs that called `GetStdHandle`/`WriteFile`, printed the expected line, and returned 37. The AMD64 PE selected `libarm64ecfex.dll` and passed five later runs across five fresh Wine prefixes. One earlier prefix produced two `0xc000001d` assertions in `FEXCore::Assert::ForcedAssertEv`; its trigger is unknown. This is a Linux reference result only; no native macOS Wine process or app launch has passed. Full hashes and logs are linked above.

## Five highest-priority tasks

1. Explain the Linux prefix-local FEX assertion against the pinned 11.16 package. Preserve the two failure logs and five clean-prefix passes, identify what state triggers `ForcedAssert`, and reach at least 10 fresh-prefix passes covering both ARM64-first and x64-first startup plus isolated FEX user paths. Do not port speculative fixes into Darwin or upstream.
2. Continue the free Apple authorization inquiry for Gate 0A. Keep the unprovisioned baseline closed; do not guess entitlement strings or relax system protections. A paid membership is not evidence that this restricted capability will be approved.
3. Keep the pinned native ARM64 Wine build recipe and one-file Darwin loader/layout patch reproducible while authorization is pursued. The two component builds and build-only loader link pass; neither has been run as a Wine process.
4. Resolve Gate 0B separately: can an independently signed runtime install and launch on an unrelated stock Mac without recipient enrollment or security changes? Developer ID signing and notarization can wait until there is a justified distribution test.
5. After Gate 0A, begin Darwin FEX/ARM64EC integration and prove thread setup, transitions, exceptions, and execution provenance before adding application support. Qualify ABI, memory, synchronization, and then a small desktop corpus; graphics and consumer UI remain later work.

These are dependencies: product UI and accelerated graphics cannot unblock missing execution authority or correctness.

Gates 0A and 0B are independent: passing 0A proves that authorized development execution is technically possible, while 0B establishes that ordinary recipients can use a distributed build. Neither implies the other. Apple's documented process and the unanswered WinFerry entitlement questions are tracked in [the authorization evidence](evidence/apple-authorization-process.md); use free support routes while paid enrollment is unavailable, and do not assume membership guarantees the capability. Native Wine component builds and the isolated loader/layout build proceed in parallel and do not substitute for running a Wine process after 0A. The two-build check has passed compilation with partial reproducibility; the loader/layout experiment verifies only generated Mach-O addresses. See the [comparison record](experiments/native-wine-build/build-comparison.md) and [loader build-only record](experiments/native-wine-build/darwin-loader-build.md). The patch queue is tracked in [the source-level port assessment](evidence/native-wine-minimal-patch-queue.md). Linux milestone 1B is a reference path, not proof of Darwin execution or a product fallback. Milestone 5's 8-of-10 criterion applies to a **predeclared** small corpus, not cherry-picked applications after testing. Publish exclusions separately. No milestone claims universal support.

Gate 0A can begin with a platform-only harness; no Wine build, x18 veneer, or signal patch is necessary to expose a capability denial. The harness should compare identical source compiled with ordinary and low-address linker layouts, capture linker/code-signature and entitlement state, and record the child-process result plus relevant diagnostics. Keep each variable explicit; do not label error 88 as an entitlement denial without corroborating evidence. Software TSO fallback can be evaluated later for FEX threads where legally available, but cannot replace missing page/layout authority. Use the local [probe record](experiments/README.md) as a starting diagnostic, not proof that either gate is complete.

## Test and benchmark discipline

**Proposed measurements:** compare identical application versions/workflows and data under native stack, an existing free Wine/Rosetta baseline where available, and UTM only where appropriate. Record hardware, OS, patches, graphics mode, RAM pressure, cache state and confidence intervals over repeated runs. Separate cold installation, launch-to-interactive, warm launch, CPU task, UI input latency, peak resident footprint/guest RAM, battery/energy and GPU workload. Record failures as failures, not zero-time successes. Choose tolerable regression thresholds for the predeclared corpus before testing; no current speed target or claimed advantage is justified by this investigation.

Correctness fixtures should compare API results and fault/exception behavior against a licensed Windows reference, not mirror the implementation. Reuse upstream Wine/FEX tests. Workload testing covers multilingual text/fonts, input methods, clipboard formats, DPI, accessibility, shell dialogs, registry/COM, file locks and child installers. Kernel drivers and anti-cheat require a different compatibility boundary and are outside this preview.

## Small reusable subsystem worth building

A **runtime manifest and evidence format** can serve Wine packaging, Hangover, UTM handoff and testing without owning a new emulator. A record should identify executable hash/version and PE architecture; imported/delay-loaded dependencies; tested runtime tuple; host OS/hardware capability; permissions; installation steps with checksums; before/after environment changes; workflow test source/results; diagnostic artifacts with redaction; and provenance/status/date. License recipe data explicitly and exclude proprietary redistributables/secrets.

A selector reads this record and host capabilities, verifies the recipe inputs, chooses one qualified path and explains the evidence. On an unknown binary it cannot prove compatibility from imports alone. It can detect PE architecture, reject required kernel drivers where identified, use a conservative default, and collect permissioned test evidence. If a downloaded plugin changes the dependency graph, invalidate the previous conclusion. This deterministic limitation is a reason to be honest, not a reason to add an AI dependency.

Recipes should describe changes declaratively and journal each mutation. Install into a disposable prefix; commit only when checks pass. Rollback must restore prefix state and report external side effects it cannot undo. Native/VM backends never share a mutable registry or prefix; only explicit app-specific document/state transfer is permitted.

## Sustainability boundary

Keep upstream Wine and FEX releases as the base. Track patch count and affected modules each release, assign human maintainers to the Darwin seam, and require build/conformance results before upgrades. FEX and DXMT forbid AI-authored upstream code; this report is research, not an authorization to submit generated port patches. [Contribution constraints](06-licensing-security.md).

The first substantial expenditure should buy proof of authorization and reproducibility. Interface work can follow that proof. If those gates fail, publish the evidence, test corpus and manifest subsystem; do not conceal a Rosetta fallback inside a product advertised as Rosetta-free.
