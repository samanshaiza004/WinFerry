# Alternative execution architectures

Cutoff: 2026-10-10. These comparisons use verified architecture and reported compatibility, not fabricated scores or benchmarks. The recommendation is an **INFERRED** engineering decision; runtime feasibility gates remain in [02](02-native-arm64-wine.md) and [07](07-feasibility.md).

## Architecture comparison

| Dimension | A: Native Wine + FEX | B: Windows ARM VM via UTM/QEMU | C: Native plus explicit Windows VM fallback | D: ARM Linux VM + Wine/FEX |
|---|---|---|---|---|
| Existing evidence | REPORTED CrossOver July ARM64 Preview; public Wine macOS patches and FEX PE integration need independently pinned build | VERIFIED documented Windows ARM installation/guest tools; application compatibility depends on Windows emulation and virtual devices | Its individual backends exist; automatic migration and equivalent user experience are UNKNOWN | VERIFIED Hangover targets ARM64 Linux; a complete Mac-integrated Linux-guest Windows application product is not demonstrated here |
| Compatibility | Wine API coverage plus guest CPU accuracy; no Windows kernel drivers | Microsoft Windows APIs present; x86/x64 user-mode apps emulated by Windows ARM; architecture-specific drivers still constrain | Union of tested backend compatibility, not universal compatibility | Wine API limits remain; Linux host work is avoided in translator but desktop/graphics remoting added |
| Performance | Native Wine calls can avoid CPU emulation; guest x86 code still translated; cost UNKNOWN without workloads | ARM guest virtualized; Windows translates x86 applications; virtual display/I/O adds boundaries | Each backend's own cost plus dispatch/provisioning; no inherent runtime speed advantage | ARM guest virtualized plus x86 translation plus presentation boundary |
| Memory/start latency | No guest OS requirement; translator caches/prefix services still consume resources | Guest OS RAM, disk, boot/resume and updates required | Paying for two installations/caches; fallback can start guest OS | Guest Linux RAM, disk and boot plus Wine prefix required |
| Packaging/security | macOS cross-architecture signing/entitlements unresolved; Wine process needs explicit isolation policy | Reuse maintained UTM; VM isolation weakened by shared directories, clipboard, devices/network | Maintain two trust models, installers and diagnostic paths | Reuse guest distro/package ecosystem; supply-chain and VM management still required |
| License/dependence | Wine LGPL/FEX MIT + macOS platform APIs; preferred path excludes proprietary graphics | UTM/QEMU open source; Windows guest and license proprietary | Cannot satisfy fully free/no-Windows vision for fallback users | Free guest runtime possible; depends on hypervisor and Linux distribution |
| Desktop experience | Wine mac driver supplies windows; macOS integration improvements plausible | UTM gives VM display/guest tools; Parallels has commercial seamless mode but is not reusable | Documents, registry, installation state and credentials differ across backends | Need remoted windows, clipboard/audio/input and file access; not direct macOS Wine driver |
| Small-team sustainability | Prefer upstream Wine/PE translator; minimize patch delta and quantify it | Best existing emergency option; authoring a new hypervisor wastes effort | Two full backends doubles qualification/support dimensions before value is proved | Avoids Darwin translator issues but creates remoting and guest lifecycle burden |

**Sources:** A follows the [Aug 7 Wine-devel report](https://list.winehq.org/hyperkitty/list/wine-devel%40list.winehq.org/thread/CKG5CEN2BE5VRXZ7O7NX4YUSBH3247WH/?sort=date) and [Hangover model](https://raw.githubusercontent.com/AndreRH/hangover/master/README.md). B follows [UTM README](https://github.com/utmapp/UTM), [guest tools](https://docs.getutm.app/guest-support/windows/) and [Windows ARM emulation limitations](https://learn.microsoft.com/en-us/windows/arm/faq). Microsoft documents [Windows license requirements](https://support.microsoft.com/en-us/windows/experience/platform-variants/options-for-using-windows-11-with-mac-computers-with-apple-m1-m2-and-m3-chips). Resource/startup comparisons are structural inferences, not measured ratios. D follows Hangover's Linux scope and is proposed architecture, not reproduced integration.

## Why C is not automatically superior

**INFERRED:** fallback is useful only for failures the alternate backend actually resolves. A kernel-driver requirement may remain incompatible in ARM Windows if only x86 drivers exist. A D3D12 game can fail in both a native Metal translation stack and the VM graphics stack. Blind retry also repeats installer side effects, login prompts, licensing activation and downloads. A crash alone does not deterministically identify the right backend.

Two installations cannot transparently share a Wine prefix and a Windows registry. Application state migration needs a separate per-application contract; mutable native and guest files must not race. A full VM solution brings Windows licensing and update burden to a project whose differentiator is avoiding them. **Recommendation:** version-one should offer an explicit link/export to an existing user-owned VM, not maintain a second built-in execution engine. Promote deeper fallback only after a fixed corpus shows substantial incremental compatibility and acceptable support cost.

## Updated VM graphics baseline

Do not assume UTM remains limited to display-only Windows graphics. **REPORTED:** [v5.0.5 beta](https://github.com/utmapp/UTM/releases/tag/v5.0.5) adds experimental DirectX with limited game compatibility and optional D3DMetal D3D12. [v5.0.6 beta](https://github.com/utmapp/UTM/releases/tag/v5.0.6), Sep 24, warns the corresponding Windows driver update is not yet available. These are evidence to investigate, not evidence of production parity with Parallels. Proprietary D3DMetal still fails the mandatory FOSS graphics requirement. [Parallels product documentation](https://www.parallels.com/products/desktop/) demonstrates vendor-reported seamless windows and D3D11 baseline, not performance equivalence or permission to reuse its implementation.

## Architecture D as a contingency

**INFERRED:** Linux-guest Wine/FEX may be preferable if Darwin execution authorization is unavailable to independent publishers. It avoids Windows licensing and reuses mature Linux PE translator integration. A meaningful first experiment would run the same x64 console fixture in an ARM Linux VM with Hangover and record architecture; a desktop prototype would then measure remoted UI latency, accessibility and memory. It sacrifices direct macOS Wine windows and no-guest-OS startup. Do not choose it merely because Linux FEX builds are easier; the overall product becomes a VM/remoting system.

A Rosetta-based Wine build is an existing transitional baseline, not a long-term solution to the stated objective. Full x86 Windows QEMU TCG is a recovery/testing option when architecture-specific drivers are needed; it emulates the OS as well as applications. UTM's own [Windows guide](https://docs.getutm.app/guides/windows/) warns about x86 multicore ordering correctness and a force-multicore option that can cause crashes. Do not use that override as a production performance shortcut.

## Decision for the main ADR

**CONDITIONAL GO on A:** first qualify signed native Wine plus FEX PE execution from public source. **Reject B as primary:** it requires Windows and contradicts the preferred-path requirements, despite being practical for some applications. **Defer C:** support user-controlled fallback only after native compatibility evidence exists. **Keep D as contingency:** if stock-Mac distribution cannot be independently authorized, assess a free Linux VM backend before abandoning the useful deterministic environment/diagnostic subsystem.

Acceptance criteria before full product commitment: same self-built x64 fixture succeeds repeatedly through native ARM64 Wine/FEX on two clean stock Apple Silicon machines; logs identify all process architectures and emulator modules; ordinary recipients have no developer enrollment; no proprietary DLL or system-protection changes; all runtime source and licenses available; at least one real desktop workflow passes a reproducible test. This document proposes criteria; it does not claim they have passed.
